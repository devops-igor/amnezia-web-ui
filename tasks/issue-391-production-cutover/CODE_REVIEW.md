## 3. Findings

### F1 — CRITICAL: bcrypt regression breaks legacy >72-byte password authentication

`internal/security/security.go` `CheckPasswordHash` was "hardened" by removing the direct-compare-first path for >72-byte passwords. Empirically proven with a real Python-generated hash (`bcrypt.hashpw(pw.encode()[:72], gensalt())`, exactly the legacy app's code):

```
CheckPasswordHash(100-byte password, legacy hash of pw[:72])  = FALSE   ← regression
CheckPasswordHash(pw[:72],           legacy hash of pw[:72]) = true
```

The old code authenticated these users (x/crypto's `CompareHashAndPassword` internally truncates at 72 bytes, verified empirically: full 100-byte pw vs hash of pw[:72] → nil error). The new code routes >72-byte passwords exclusively through SHA-256 pre-hash, which can never match a legacy `bcrypt(pw[:72])` hash. **A legacy user with a >72-byte password is locked out after cutover.** This directly violates TASK.md §2.1.4 and flips Done-Done criterion #7 (Crypto Compatibility) to NOT SATISFIED.

Blast radius (all three call sites pass the raw password; none truncate first, so nothing mitigates elsewhere): `handlers/auth.go:173` (login), `handlers/auth.go:320` (change-password current-password check), `handlers/share.go:67` (share-password auth) — users with >72-byte UTF-8 passwords AND >72-byte share passwords are affected. Users with ≤72-byte passwords are unaffected (verified: 'AdminPassword123!' authenticates post-diff).

Why the test suite missed it: `migration_compat_test.go` generates its "legacy bcrypt hashes" by calling Go's own `security.HashPassword` — circular. No real Python-generated hash of a long password is ever tested. Same for the pre-existing `TestBcryptPythonCrossVerification`: I verified in Python that its `pyLongHash` vector matches `bcrypt(sha256(pw))` — Go's scheme — NOT the legacy `bcrypt(pw[:72])`; the vector was mislabeled from the start. The only hardcoded genuine Python hash in the suite (`security_test.go:162`) is for a 19-byte password — the one case that couldn't fail. The full suite passes post-diff, confirming the tests mask the regression rather than catch it.

**Fix:** restore the dual-path in CheckPasswordHash (try direct compare first, then pre-hash) or document a forced password reset; add a test vector generated by actual Python `bcrypt.hashpw(pw[:72], ...)`.

**Independent confirmation:** An isolated reviewer subagent (no shared context, own scratch binary pinned to x/crypto v0.56.0, genuine Python-generated vector) reproduced exactly this failure and returned verdict BLOCK with high confidence: `legacy_python_gt72byte_hashes_still_authenticate_after_change: false`, `test_suite_genuinely_verifies_legacy_python_generated_hashes: false`.

**Related gap (F1b):** legacy Python `verify_password` also supports pre-bcrypt PBKDF2 hashes (`salt$hex`, 100k iterations — `app/utils/helpers.py:149-163`). The Go codebase has **zero** PBKDF2 handling (grep confirms). Any surviving pre-bcrypt user from an old install cannot authenticate in Go either. Either implement the PBKDF2 verify path or explicitly document it as out of scope for this migration.

`docs/migration-runbook.md` instructs operators to expect:

```
INFO Additive schemas checked: backend_tunnels, vpn_sessions, vpn_config
```

None of these strings exist anywhere in the codebase (grep returns nothing). The actual startup logs (from a live run) are:

```
INFO Background orchestrator started boot_delay=1m0s interval=10m0s

```

An operator following the runbook during a production cutover would believe startup failed. Also §5.2: actual health response is `{"status":"ok","version":"1.0.0"}`, not `{"status":"ok"}`.

### F3 — HIGH: Runbook §6 rollback claim "legacy container can run directly against the updated SQLite database" is only partially true

Two data-degradation vectors exist and are undocumented:

1. **Xray private keys are irreversibly stripped** from `servers.protocols` JSON on first Go boot (`migrateXraySensitiveKeys` rewrites the rows). Rolling back loses `reality_private_key` — Xray/XTLS connections can't be regenerated from the DB. (The flag-gated stripping is legacy-parity, but the runbook's "zero data degradation" wording hides the loss.)
2. **schema_version format change**: Go writes `'"1"'` (JSON string), legacy Python reads with `int(row["value"])` → ValueError → returns 0 → Python re-runs migrations and re-writes the value. Mostly harmless, but it contradicts "without errors" and the formats were previously divergent (the compat test seeds `'"1"'` — matching Go's format, not Python's `"1"`).

The runbook should state: restore the pre-migration backup when rolling back, and do not rely on in-place rollback.

### F4 — MEDIUM: Done-Done criterion #2 (API parity) — legacy POST paths return 404

Live-probed the built binary: `POST /api/my/connections/add` (legacy Python path, used by legacy templates) → **404** on the Go server; the spec-relocated `POST /api/connections/add` → 400 (exists). Same for `{id}/delete`, `{id}/kit`, `{id}/rename`, `{id}/config`. The Go-ported templates were updated to the new paths, so the UI works — but any external scripts, bookmarks, or API clients against the documented legacy contract break. "All 54 existing API endpoints respond with identical status codes" is not true for these 5 POST endpoints. The spec (§1.1) declares `/api/connections/*` ground truth, so either the spec or the parity claim needs correcting — currently the docs contradict each other.

### F5 — MEDIUM: Done-Done criterion #3 — VPN endpoint count is defensible (counting nit)

The Go router registers 9 distinct `/api/vpn/*` paths = 10 verb+path combinations (status, backends list, enable, disable, tunnels, config GET, config POST, disconnect, my-connection, my-config). "All 10 new VPN endpoints" is correct under verb+path counting (the standard convention), so criterion #3's number is fine. Noted here only because QA "verified" it without stating the counting convention.

### F6 — MEDIUM: Startup "Expected: 0.6s" style claims vs measured

- Startup: measured ~20ms cold → the <50ms claim HOLDS.
- RSS: measured 18.4MB idle → "~15MB" is optimistic but within marketing tolerance.
- Image size ~38.6MB: unverifiable here (Docker not installed on this host). Note Dockerfile's own comment says "~41MB", and the previous phase's handover claimed <30MB — the numbers drift between documents.

### F7 — LOW: coverage table numeric drift between handover and reality

Handover's verbatim Gate 2 transcript shows `cmd/server` 71.6%; actual current run yields 70.1%. Timings also differ (83.7s vs 76.4s for database). The transcripts are plausible re-runs, but "verbatim" is not accurate; treat numbers as approximate.

### F8 — LOW: Test seeds `schema_version` as `'"1"'` (Go format) in a "legacy Python" database

The compat test's legacy snapshot DB uses Go's JSON-string format for schema_version, whereas actual legacy Python DBs contain plain `1`. The test therefore doesn't exercise the true legacy value. Minor, since Go's reader handles both — but it's another example of the "legacy" fixture being generated from Go's own behavior rather than Python's.
